# PM 工具功能调研（第三轮）· 方案（2026-09-06）

> 前置：v1.4 已实现前两轮全部 16 项功能（见 [增补方案实现说明.md](增补方案实现说明.md)）。
> 本轮 4 路并行调研此前未覆盖的领域：概率预测与流程度量、会议/决策/干系人、笔记知识管理、时间预算与 Windows 桌面级效率。
> 筛选标准不变：**单人本地使用是否有价值 × 原生 JS/Rust 实现成本 × 与现有功能协同**。只出方案，不改代码。

## 一、四大主题调研结论摘要

### 1. 概率预测与流程度量（ActionableAgile / Nave / Vacanti / LiquidPlanner）
- 蒙特卡洛交付预测的最小数据集**只需要 tasks.doneAt**（按天聚合即吞吐量序列，约 3 个月历史即可）；经验重抽样 500~10000 次在 JS 里毫秒级完成。对领导最有说服力的输出是三行置信表：**"100 项：50% 于 5/16、85% 于 6/29、95% 于 7/26 完成"**，且可直接走已有群 Webhook 话术推送。
- 小数据口径调整：按周聚合、只给 50/85 两档、标注"基于最近 N 项"。
- WIP Aging 用历史 cycle time 的 85 分位做离群线，比现有停滞检测的固定 7 天阈值更科学——两者可叠加。
- LiquidPlanner（$15-42/人/月，现为 Tempo Portfolio Manager）证明"两数字区间估算 + 概率排期"是付费卖点，但全量引擎不适合单机；PERT 需要依赖网络，与吞吐量法互斥，后者无需估算更适合本工具。

### 2. 会议 / 决策 / 干系人（Fellow / Geekbot / ADR / FollowUpThen）
- Fellow（$7/人/月）验证的核心交互：**行动项必须落成个人任务才有人追**；Hugo 停售说明纯协作层难活，但"按干系人聚合会议史"的交互单机完全成立。
- 决策日志（ADR 模板：背景/选项/决定/原因/日期）是性价比之王——直接命中"口头答应了没人记得"；ClickUp/Confluence 均有现成模板字段可抄。
- 干系人跟进的极简机制 = FollowUpThen 的本质：「联系人 + 上次沟通日期 + 循环周期」→ 过期自动生成"跟进某人"任务进今日聚焦。
- 异步站会三问与已有"收尾问答"同构，属增强而非新建。
- 会议成本 = 人数×时长×时薪，锦上添花（低优先级）。

### 3. 笔记 / 知识管理（Obsidian / Logseq / Tana / Notion / Coda）
- PM 社区公认最小组合：**每日笔记（当日任务自动注入）+ 会后笔记模板 + 人员反链聚合**；痛点原话："当时为什么这么定"找不到。
- Logseq 新 DB 版底层也是 SQLite，佐证本工具路线；社区共识架构是"文件为真源、SQLite 为索引"，反向双写易漂移——所以**导出快照足够，不做实时双写**。
- Tana 的万物节点是过度设计；只借鉴"字段模板"思想（会后笔记、风险条目用预设模板）。
- 优先级：Markdown 富文本备注 → 每日/会后笔记 → [[反链]] → 项目 one-pager → 整项目 MD 导出。

### 4. 时间预算 / 自动追踪 / Windows 桌面集成（Toggl / Harvest / ActivityWatch / Tauri 插件）
- 工时预算告警是 Toggl 的 Starter 付费卖点，而本工具已有 time_logs + 通知管道 + 日报，**边际成本极低**：项目设 budget_hours，80%/100% 触发托盘通知 + 群推送 + 报告附燃烧率。
- 自动追踪前台窗口技术上可行（ActivityWatch 开源可参考，本地存 SQLite 不传云），但匹配规则维护 + 隐私观感是长期负担，建议实验性开关、默认关。
- Tauri 2 桌面端能力盘点：**全局快捷键（官方插件，支持良好）、任务栏进度条（官方 API set_progress_bar，低成本高感知）、深链接+单实例（官方 deep-link 插件）、开机自启（官方 autostart）**；交互式 Toast 按钮桌面端需 windows-rs 自绘（半坑）；Jump List/Badge 无官方支持；剪贴板监听与 Share Target 建议放弃（隐私/打包限制），用"命令面板：从剪贴板建任务"替代。

## 三、明确不做 / 观望

| 项 | 结论 | 原因 |
|---|---|---|
| LiquidPlanner 式全量概率排期 | 不做 | 需容量+依赖引擎，单人不划算 |
| PERT/关键路径 | 不做 | 需要依赖网络数据，与吞吐量法路线冲突 |
| 交互式 Toast 按钮 | 观望 | Tauri 桌面端官方不支持，需 windows-rs 自绘 Toast XML |
| 前台窗口自动时间追踪 | 实验性开关、默认关 | 技术可行（ActivityWatch 先例），但规则维护+隐私观感负担重 |
| Jump List / 任务栏徽标 | 观望 | 无官方插件，收益低；托盘 tooltip 可替代 |
| 剪贴板后台监听 / Share Target | 不做 | 隐私观感/杀软误报/MSIX 打包限制；用「从剪贴板建任务」命令替代 |
| 实时 MD 双写同步 | 不做 | 双源易漂移；导出快照足够 |
| CFD 累积流图 | 缓 | 需新增状态流转事件表开始记录历史，等包 1 数据沉淀后再画 |

## 四、建议实施顺序

1. **包 1（2~3 天）**：与现有 doneAt/time_logs 数据零迁移，产出直接进日报与群推送——最快见效。
2. **包 2（2~3 天）**：纯 Rust/插件侧，UI 改动小，一次发版全带上。
3. **包 3（4~5 天）**：决策日志优先（性价比最高），会议记录其次。
4. **包 4（5~7 天）**：拆散按需做；若用户开始要"项目档案/交接文档"，优先 13/14/15。

## 五、增补（用户补充需求）：Excel 计划表导入 / 导出（包 5）

> 场景：中国 PM 的高频输入不是"自己想任务"，而是**收到甲方/领导/协作方发来的 Excel 计划表**（WBS 表、进度表、里程碑表），需要把它变成自己系统里能盯的任务。参考产品：Jira CSV 导入向导（表头驱动映射→值映射→预览→导入报告）、明道云（选文件→选表→选表头→字段映射）、OpenProject（子任务用 4 空格缩进表示层级）。

### 导入向导五步（Jira 模式为骨架）

1. **选文件**：支持 .xlsx / .xls / .csv（WPS 用户提示"另存为 xlsx"即可；.et 不直接解析）。前端用 SheetJS（js-xlsx，Apache-2.0，本地解析无网络依赖）或 Rust calamine 读。
2. **选工作表 + 表头行**：列出所有 sheet；自动猜表头行（首个含「任务/事项/工作内容/名称」类关键词的非空行），允许手改。
3. **列映射**：本地字段下拉映射——标题（必填）、结束时间→due、开始时间（可写入备注或新增 start 字段）、负责人、优先级、状态/完成百分比、备注/交付物、所属阶段。**自动预映射**：按列名关键词猜（"截止/完成时间/计划结束"→due，"负责人/责任人/Owner"→负责人）。**值映射页**（Jira 特色）：把表里的「已完成/100%/done」→done、「进行中/实施中」→doing、「未开始/待启动」→todo 逐值勾选。
4. **预览（dry-run）**：前 20 行表格预览 + 逐行校验（日期解析失败、标题为空 → 标黄/标红），汇总"N 行可导入，M 行有警告"。
5. **导入选项与报告**：新建项目（项目名默认取文件名/sheet 名）或并入现有项目；完成后给导入报告（成功 N 条、跳过 M 条及原因），支持"先导到示例项目试一把"（Jira 最佳实践）。

### 真实计划表的脏数据策略（中国特供）

| 脏点 | 策略 |
|---|---|
| 合并单元格 | 解析合并区域并向下填充首值（通用方案：识别区域→非首行取首值） |
| 阶段/任务混排（WBS 层级） | 三路自动探测：①序号列点分层级（1 / 1.1 / 1.1.2）②单元格缩进/前导空格（OpenProject 4 空格规则）③独立「阶段」列合并单元格。**阶段行→父任务**（写入 parent_id），任务→子任务——直接复用 v1.4 已有的父任务进度上卷，导入完成阶段进度自动算 |
| 日期格式混乱 | 2026-09-01 / 2026/9/1 / 9月1日 / Excel 序列号（cellDates）全兼容；"9月上旬"这类模糊表述标黄让人工处理 |
| 完成百分比 | 50%、0.5、"50" 统一归一；≥100% → done，1~99% → doing（可选开关） |
| 无日期列 | due 默认留空/今天，预览页醒目提示 |
| 前置任务/依赖列 | 暂无依赖模型 → 原文写入备注（"前置：XX"），不做依赖解析 |

### 姊妹功能：导出 Excel 计划表（0.5~1 天）

现有 CSV 导出旁加「导出 .xlsx」：按阶段分组、带样式表头、含状态/风险值/负责人——把系统里的计划**反向发回**给甲方/领导，和导入形成双向闭环（对标 OpenProjectExcel 的双向同步思路，但做成快照式导出，不做实时同步）。

### 明确不做

- **.mpp（MS Project）导入**：需要 Java MPXJ 运行时，过重；提示用户先从 Project 导出 Excel。
- 多 sheet 关联解析、导入时自动建依赖关系。

### 成本与排期

导入向导约 2~3 天（解析规则是大头）+ 导出 xlsx 0.5~1 天，合计 **3~4 天，作为包 5**；建议排在包 1、包 2 之后（包 1 的交付预测让导入进来的计划马上有"哪天能做完"的答案，组合价值更高）。

主要参考：[Jira CSV 导入官方文档](https://support.atlassian.com/jira-cloud-administration/docs/import-data-from-a-csv-file/)、[Jira DC 导入与值映射](https://confluence.atlassian.com/adminjiraserver/importing-data-from-csv-938847533.html)、[明道云 Excel 建表流程](https://help.mingdao.com/worksheet/import-excel-create/)、[OpenProject Excel 同步（缩进表层级）](https://www.openproject.org/docs/system-admin-guide/integrations/excel-synchronization/)、[OpenProjectExcel 开源实现](https://github.com/opf/OpenProjectExcel)、[Excel 合并单元格解析通用方案](https://blog.csdn.net/weixin_43905826/article/details/149754986)、[js-xlsx 前端解析实践](https://blog.csdn.net/u014241231/article/details/122615830)

## 六、产品定位（确认稿）

> 此前两轮的功能取舍都是逐条判断，这里把隐含的判断标准显式化，作为后续所有功能决策的依据。

**一句话定位**：给「同时盯 N 个项目的项目经理」的本机个人作战台（Personal PM Cockpit）——把**捕获任务 → 盯进度 → 对上汇报**这条闭环做到本地单机的极致。

**不是什么**（三条边界，功能撞线即拒）：
1. **不是团队协作平台**——不做多人、权限、审批、评论流（钉钉/飞书的地盘；Hugo、Height 等纯协作层工具接连停售也佐证单人层要独立成立）。
2. **不是排程引擎**——不做依赖驱动的自动重排、资源均衡、关键路径（MS Project/GanttProject 的地盘）。时间承诺用「**呈现 + 概率预测**」表达，不用「计算排程」表达。
3. **不是通用知识库**——不做双链笔记图谱、不做文档站（Obsidian/语雀的地盘），只做与任务/项目/决策绑定的浅笔记。

**核心闭环**：快速捕获（快速添加/全局热键/Excel 导入）→ 多视图跟踪（列表/看板/日历/时间线/统计/智能视图）→ 汇报产出（日报周报/交付预测/导出截图/Excel）→ 群推送（钉钉/企微/飞书）。

**新功能准入三问**（裁决法则）：
1. 去掉协作假设后，单人本地用是否仍有价值？
2. 能否复用现有数据结构（tasks/time_logs/ideas），而不是引入新引擎？
3. 产出物能否流入「汇报」链路（日报/群推送/截图/导出）？
—— 三问中两个「否」即进观望或拒绝。

**甘特图按此裁决**：调度型甘特（依赖表 + 自动重排 + 资源 + 基线引擎）三问全不中 → **不做**（维持原判）；汇报型时间线（呈现时间承诺 + 导出截图发领导）三问全中 → **做**，即下节包 6。

## 七、甘特图专题：结论与方案（包 6）

> 推翻前两轮「甘特图不做」的结论。推翻的理由：此前把甘特图等同于调度引擎，但调研表明市场主流的「现代轻量时间线」（Asana Timeline、Notion Timeline、飞书/Teambition 甘特）早已砍掉 SS/FF/SF 依赖、自动重排、资源均衡——**依赖连线是可选项而非甘特的门槛**；而本工具数据本来就在库里（due/状态/进度上卷），打开即自动重渲染，恰好消灭了汇报型甘特「数据一变就过时」的最大痛点。

### 调研依据

- **重型引擎的最小数据模型**：start+duration（或 finish）、工作日历、依赖表（FS/SS/FF/SF+lead/lag）、约束、资源分配、基线快照——自动重排与关键路径必须依赖全表（[依赖类型](https://hcp-consulting.com/dependencies-in-schedules/)）。GanttProject 刻意砍掉资源均衡仍是"真甘特"，砍掉依赖+重排则退化为时间线——我们选择退化为时间线，且是有意为之。
- **现代 SaaS 时间线的真实边界**：都要求 start+end 两个日期（[Notion Timeline](https://www.notion.com/help/timelines)）；Asana 拖条改期/拖边改工期/弹窗问顺延；Monday/Wrike 只有 FS 依赖、无关键路径宣传；通行形态=左任务表+右周/月网格+今日线+里程碑菱形+进度填充。
- **单人小项目争论**：调度无意义（<50 条任务脑内可排、维护依赖边成本>收益），但**呈现时间承诺**极有价值——「被问哪天交付、要发截图」正是甘特的主场而非看板的。
- **国内对标**：飞书项目有基线/自动排期（重型）；TAPD 甘特支持[导出图片和 Excel](https://cloud.tencent.com/document/product/624/101537)——「导出图」是对上汇报的一级功能。

### 落地方案（包 6，自绘路线约 4~6 天）

| 项 | 方案 |
|---|---|
| 新增数据 | `tasks.start_date`（可空，NULL 回退 created_at 或本周一）；里程碑=任务标志 `is_milestone`（菱形渲染，不建新表）；阶段上卷条=min(start)~max(due)+进度——**直接复用 parent_id** |
| 视图 | 第 5 个视图 Tab「时间线」：左侧任务树（按阶段分组）+ 右侧网格；日/周/月三档缩放；任务条=start→due，doing 进度填充、done 绿、wait 灰、逾期红边；今日线；日档周末底纹 |
| 交互 | 默认只读 + 轻编辑：拖条改 start+due、拖边改 due（吸附到天，复用现有看板指针拖拽代码）；**不做依赖连线** |
| 导出 PNG | **一级功能**：若走 SVG 渲染，序列化→img→canvas 约 30 行零依赖、任意尺寸高清（WebView2 下最稳）；避免 html2canvas 类重绘 CSS 的兼容坑 |
| 实现路线 | **推荐自绘**（4~6 天：布局渲染 2d、缩放滚动 1~1.5d、拖拽 1d、导出 0.5~1d、打磨 1d）——项目零构建链、UI 定制多（分组/上卷/逾期/进度全是自己的 CSS）、SVG 导出零依赖；备选 Frappe Gantt（MIT、14KB gzip、活跃）3~4 天但里程碑/分组需魔改且导出仍要引第三方；dhtmlx v10 功能最全但 175KB、风格难融；vis-timeline 无分组/进度概念；DevExtreme 无免费商用许可——均不选 |
| 排期 | 可拆两步交付：第一步只读渲染+导出 PNG（2~3 天即见效，直接服务汇报），第二步拖拽编辑 |

### 明确不做（甘特专项）

SS/FF/SF 与 lead/lag、自动重排、资源均衡、关键路径、基线表（周报快照可后置替代）、紧凑装箱行分配（每任务独立行 + 阶段上卷已够用）。
